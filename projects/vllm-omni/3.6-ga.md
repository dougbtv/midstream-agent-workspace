## Prior released RC validation — November 3

[INFERENG-11902](https://redhat.atlassian.net/browse/INFERENG-11902)

The corrected [nm-cicd run 41664893948](https://github.com/neuralmagic/nm-cicd/actions/runs/41664893948)
used `config_ref=main`; registry authentication, image inspection, SBOM
collection, model-config checkout, and OCP deployment setup all passed. The
seven-model smoke matrix finished **1/7 passed**.

The six failures reduce to two shared causes:

1. **Released-image dependency defect — three engine startup failures.**
   Qwen3-Omni, Qwen3-TTS CustomVoice, and Voxtral TTS fail before serving a
   request. The released-image SBOM contains `flashinfer-python==0.6.18.post1`,
   `flashinfer-cubin==0.7.1`, and `flashinfer-jit-cache==0.7.0.post1+cu130`.
   Runtime failures are either the explicit cubin/Python version check or the
   missing `flashinfer_jit_cache.get_jit_cache_dir` API. The selected
   `nm-vllm-ent` `v0.30.0+rhaiv.1` CUDA requirements pin all three packages to
   `0.6.18.post1`, but the containers commit `20fe60f` listed the three
   FlashInfer packages as unversioned direct dependencies. Its generated
   hermetic lock therefore admitted mutually incompatible latest packages.
   This is a release blocker; do not use `FLASHINFER_DISABLE_VERSION_CHECK=1`
   as disposition because it bypasses the guard without restoring API or
   kernel compatibility.
2. **Validation-contract question — three diffusion smoke failures.**
   FLUX.1-schnell, FLUX.2-dev, and Z-Image-Turbo started and completed the
   other exercised inference paths, but accepted an empty prompt where the
   smoke harness expects rejection. Decide whether empty prompts are supported
   diffusion behavior. If yes, narrow the harness expectation; if no, add
   server-side validation. This does not explain the engine crashes and should
   not block producing a FlashInfer-corrected candidate.

FLUX.2-klein-4B passed. The CI failure analyzer recorded the two signatures in
[nm-cicd #1604](https://github.com/neuralmagic/nm-cicd/issues/1604) and
[nm-cicd #1605](https://github.com/neuralmagic/nm-cicd/issues/1605). The
detailed release handoff is in
[the November 3 validation note](../../notes/handoffs/2026-11-03-infereng-11902-omni-final-rc-validation.md).

Required corrective path at that time: pin the FlashInfer trio to a compatible, reviewed set
(the selected source contract is `0.6.18.post1`), regenerate and review the
dual-architecture lock, build a new immutable candidate, verify its SBOM, and
rerun the three startup failures plus the full seven-model matrix. Record the
diffusion empty-prompt disposition separately. The corrected interim image is
recorded above; the final-RC target was subsequently moved to November 16.

## Reduced scope

The fast1 phase established the hard, previously unknown path: Midstream builds,
AIPCC wheels, release-branch container integration, Konflux builds and release,
and OCP validation. The 3.6 GA phase should reuse that path and focus on deltas.

### Midstream scope assessment

The September 18 assessment sent to Selbi concluded that the new PM/OCTO STRATs
do not expand the baseline Midstream scope on their own. The planned Midstream
work remains selected-version sync and release integration, triaged technical
debt, the existing carry inventory, agreed model additions, build/tag handoff,
and release validation.

Feature owners and SMEs are expected to merge implementation upstream in time
for inclusion in the selected vLLM-Omni tag. A feature that misses that path is
not automatically inherited by Midstream. It becomes a proposed net-new feature
carry, which is rejected by default under
[nm-vllm-omni-ent PR #55](https://github.com/neuralmagic/nm-vllm-omni-ent/pull/55).
An exception requires a Jira issue with an accountable component owner, upstream
PR and merge plan, bounded patch and risk, test plan or automated tests, and
explicit Release Owner approval before merge.

### In scope

- Confirm release dates, planning freeze, upstream and Midstream version targets,
  and responsible stakeholders.
- Finalize the release model list and reconcile it with the shared spreadsheet
  and CI configuration.
- Perform the required upstream sync, Midstream build/tag, and downstream version
  bumps.
- Start the selected-version sync from a clean upstream tree, drop carries already
  present upstream, and record the owner, upstream relationship, and test plan or
  automated tests for every surviving carry.
- Prove that published wheels contain required deploy configs and runtime assets;
  source-checkout tests are not sufficient packaging evidence.
- Verify that the established AIPCC/Konflux release path still works for the
  selected version.
- Validate the agreed model matrix against the release candidate image.
- Record immutable image identity, validation evidence, known limitations, and
  release disposition.

### Out of scope unless a concrete release blocker appears

- Repeating AIPCC architecture discovery or rebuilding the already-proven
  productization flow.
- Broad CI redesign, blanket elimination of every carry, or unrelated TP.next
  work. The release owns a bounded carry audit and explicit ownership, not an
  open-ended cleanup program.
- Treating the 3.6 GA release name as a commitment to graduate Omni from Tech
  Preview.
- Pulling every TP.next enhancement into the release critical path.

## Carry ownership boundary

The 3.6 GA sync should begin with the selected upstream tree and reapply only
what the release still needs. Every surviving carry must record its reason,
repository or component area, named owner, upstream issue or PR where applicable,
and test plan or automated tests.

- **Midstream-owned carries:** packaging metadata, requirements filtering,
  build-system integration, UBI/container behavior, and release infrastructure.
- **Component-owned carries:** vLLM-Omni model features, APIs, runtime behavior,
  and component correctness. These require an individual, SME, or team owner;
  Midstream may coordinate the release but does not become the permanent feature
  owner by default.
- **Net-new feature carries:** rejected by default. Any exception is an explicit
  release decision in Jira under the PR #55 policy; approval does not transfer
  implementation or backport ownership to Midstream.

INFERENG-10172 completed this release boundary: already-upstreamed carries were
dropped and the remaining narrow set is reviewable and owned. It did not require
eliminating every carry before release.

For a capability to remain committed at Planning Freeze, its SME must provide a
human-reviewed scope and acceptance criteria, explicit Fix Version and owner,
repository-qualified upstream reference and timing, owned cross-team
dependencies, exact model/API validation scenario, and any required carry or
backport with an owner and test plan or automated tests. A net-new feature carry
also requires explicit Release Owner approval in Jira. Missing inputs mean the
capability is not committed; they do not silently become Midstream implementation
work.

## Entry criteria for implementation

- 3.6-fast2 disposition is confirmed rather than inferred.
- 3.6 GA planning freeze and release milestones are known.
- Upstream and Midstream version targets are agreed.
- The release model list is finalized or explicitly marked provisional with an
  owner and decision date.
- Release-gating work is separated from durable TP.next improvements.

## Definition of done

- Scope, milestones, version target, and model list are documented.
- Required Midstream and downstream changes are merged with linked evidence.
- The selected base-vLLM v0.30.0 commit has a durable protected release branch
  and tag independent of the v0.31.0 `main` line.
- Every surviving carry has an explicit owner, upstream relationship, and test
  plan or automated tests; net-new feature carries have explicit Release Owner
  approval in Jira. The release does not silently transfer component-feature
  maintenance to Midstream.
- Built-wheel inspection proves required deploy configs and runtime assets are
  present.
- The release candidate passes the agreed validation matrix, with any exceptions
  explicitly accepted and recorded.
- Final image identity and support limitations are documented.
- Stakeholders have a clear release disposition, while Omni remains labeled Tech
  Preview.
