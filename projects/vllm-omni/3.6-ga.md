# vLLM-Omni — RHOAI 3.6 GA Release Planning

Status: **active planning; scope and dates not yet confirmed** — updated 2026-09-15

## Naming and support status

This document tracks vLLM-Omni work for the **RHOAI 3.6 GA release train**.
The release is named “3.6 GA,” but vLLM-Omni is currently expected to **remain
a Tech Preview** in it. Nothing in this plan implies graduation of the feature
to General Availability.

Planning epic: [INFERENG-10710 — vLLM-Omni Midstream: RHOAI 3.6 GA release planning](https://redhat.atlassian.net/browse/INFERENG-10710)

## Release sequence

1. **3.6-fast1** — first released Omni Tech Preview; the large AIPCC integration
   and initial downstream release proof were completed here.
2. **3.6-fast2** — next release increment. Current working information is that
   Omni missed its planning freeze, so image/model changes may be limited or
   absent; this still needs explicit confirmation.
3. **3.6 GA** — the next active planning phase for Omni, while retaining Tech
   Preview support status.

The full fast1 history and evidence remain in [tech-preview.md](./tech-preview.md).

## Reduced scope

The fast1 phase established the hard, previously unknown path: Midstream builds,
AIPCC wheels, release-branch container integration, Konflux builds and release,
and OCP validation. The 3.6 GA phase should reuse that path and focus on deltas.

### In scope

- Confirm release dates, planning freeze, upstream and Midstream version targets,
  and responsible stakeholders.
- Finalize the release model list and reconcile it with the shared spreadsheet
  and CI configuration.
- Perform the required upstream sync, Midstream build/tag, and downstream version
  bumps.
- Start the selected-version sync from a clean upstream tree, drop carries already
  present upstream, and assign an owner and removal condition to every surviving
  carry.
- Prove that published wheels contain required deploy configs and runtime assets;
  source-checkout tests are not sufficient packaging evidence.
- Verify that the established AIPCC/Konflux release path still works for the
  selected version.
- Validate the agreed model matrix against the release candidate image.
- Record immutable image identity, validation evidence, known limitations, and
  release disposition.

### Out of scope unless a concrete release blocker appears

- Repeating AIPCC architecture discovery or rebuilding the already-proven
  productization flow.
- Broad CI redesign, blanket elimination of every carry, or unrelated TP.next
  work. The release owns a bounded carry audit and explicit ownership, not an
  open-ended cleanup program.
- Treating the 3.6 GA release name as a commitment to graduate Omni from Tech
  Preview.
- Pulling every TP.next enhancement into the release critical path.

## Carry ownership boundary

The 3.6 GA sync should begin with the selected upstream tree and reapply only
what the release still needs. Every surviving carry must record its reason,
repository or component area, named owner, upstream issue or PR where applicable,
and removal condition.

- **Midstream-owned carries:** packaging metadata, requirements filtering,
  build-system integration, UBI/container behavior, and release infrastructure.
- **Component-owned carries:** vLLM-Omni model features, APIs, runtime behavior,
  and component correctness. These require an individual, SME, or team owner;
  Midstream may coordinate the release but does not become the permanent feature
  owner by default.
- **Unowned feature carries:** explicit scope/staffing decisions in INFERENG-10717,
  not silent additions to Midstream's maintenance load.

INFERENG-10172 is complete for this release when already-upstreamed carries are
dropped and the remaining ledger is reviewable and owned. It does not require
eliminating every carry before release.

## PM capability input (September 14)

Yuchen's current P1 requirements for “3.6 Stable” also introduce API and
compliance dependencies. They are planning inputs, not yet a committed
Midstream-owned scope.

### Capability and dependency inventory

- Audio/image/video watermarking, starting with TTS audio; the stated driver is
  the EU AI Act synthetic-audio watermarking deadline of December 2, 2026.
- `/v1/realtime` WebSocket support beyond Qwen3-Omni, including full-duplex and
  turn-based cases.
- KServe WebSocket passthrough for the full-duplex deployed-stack path.
- `/v1/audio/translations` for dedicated audio-to-text translation.
- `/v1/audio/speech/batch` and `/batches` support for TTS workloads.
- PII redaction in TTS logs, tracked by INFERENG-10008 and treated as security
  work rather than an ordinary correctness bug.

The source document cites PRs #7366, #5727, #7339, #7386, and #7277 without
repository-qualified links. Resolve and verify those dependencies before using
their status in release decisions.

### Ownership boundary

Midstream should own validation of the agreed models and API paths in the
Midstream-built image and released stack, plus the required CI/OCP coverage.
Core API implementations, upstream model enablement, watermarking, and KServe
WebSocket passthrough likely belong to partner or upstream owners. Link their
trackers where they gate Midstream validation; do not duplicate their
implementation work in this epic.

## Entry criteria for implementation

- 3.6-fast2 disposition is confirmed rather than inferred.
- 3.6 GA planning freeze and release milestones are known.
- Upstream and Midstream version targets are agreed.
- The release model list is finalized or explicitly marked provisional with an
  owner and decision date.
- Release-gating work is separated from durable TP.next improvements.

## Definition of done

- Scope, milestones, version target, and model list are documented.
- Required Midstream and downstream changes are merged with linked evidence.
- Every surviving carry has an explicit owner and removal condition; the release
  does not silently transfer component-feature maintenance to Midstream.
- Built-wheel inspection proves required deploy configs and runtime assets are
  present.
- The release candidate passes the agreed validation matrix, with any exceptions
  explicitly accepted and recorded.
- Final image identity and support limitations are documented.
- Stakeholders have a clear release disposition, while Omni remains labeled Tech
  Preview.

## Open questions

- Did Omni definitively miss the 3.6-fast2 planning freeze, and what is the final
  cutoff for Octo/upstream changes?
- Will fast2 and 3.6 GA use the same Omni image and model set?
- What upstream vLLM/vLLM-Omni version will 3.6 GA consume?
- Which model list is release-gating, and which models are informational or
  best-effort?
- Which parts of the fast1 release path require an explicit rerun versus simple
  version updates?
- What GuideLLM evidence, if any, should be part of the 3.6 GA release decision?
