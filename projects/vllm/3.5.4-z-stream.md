## Working responsibilities and release loop

3.5.4 is a **pipeline-era z-stream**. This is deliberate: the snippets state
that every z-stream remains on the pipeline path, even after a later GA moves
to fondue. Therefore the expected flow is not merely a version bump:

1. **Triage and integrate fixes.** Compare the latest released z-stream images
   with the desired state; account for CVEs in base images, pipeline
   dependencies, and `nm-vllm-ent`; merge required backports to the 3.5
   release branches. Track vulnerability Jira children under the epic.
2. **Prove the midstream change.** Run the appropriate `nm-cicd`
   `accept-sync` and image-validation workflows for a candidate
   `nm-vllm-ent` PR. A green wheel build alone is insufficient; retain links
   to successful test, evaluation, and image evidence.
3. **Build the downstream candidate.** Update/merge the AIPCC pipeline and
   containers inputs (wheel releases and base-image tags as applicable), then
   wait for the downstream Quay images for the exact target branch/commit.
4. **Validate images per lane.** Run Snyk and the applicable
   `model-validation-ocp` validation for CUDA, ROCm, and CPU; arrange the
   external lane checks called out by the stories (IBM for Spyre; AMD sharing
   for CPU). Model-opt needs its dedicated image validation rather than a
   `vllm serve` OCP smoke.
5. **Release handoff.** The epic requires final midstream-image evidence and a
   handoff to AIPCC CI/CD for the production build. For a z-stream,
   `stage-rc` is optional: confirm whether the release owner wants a stage
   round or final-to-prod directly. Do not request it until the exact Quay
   images have passed smoke and Snyk gates.

Any bug found after a candidate validation returns the effort to step 1.

## Learning reference: 3.4.7 refresh

Willy's [containers MR !1628](https://gitlab.com/redhat/rhel-ai/rhaiis/containers/-/merge_requests/1628)
is a useful concrete example, but it is **not** 3.5.4 release evidence. It
merged to the `3.4` branch on 2026-11-04 and refreshed five container argfiles:
CPU, CUDA, ROCm, Spyre, and model-opt. It aligned `RHAIIS_VERSION=3.4.7`, moved
their base images from the prior 3.4.x releases, and advanced all wheel inputs
from `3.4.4626` to `3.4.4837` with the dependency-CVE floors. The outstanding
verification noted in that MR was rebuilt-image Snyk confirmation.

The associated [accept-sync run](https://github.com/neuralmagic/nm-cicd/actions/runs/41849718116)
demonstrated the right kind of pre-downstream evidence: CUDA wheel build and
most test/evaluation partitions completed successfully, including the
dependency-floor report test. It also had an image-build failure and was still
in progress when checked, so it must not be described as green release
validation. This is exactly why each gate needs a recorded terminal result.
