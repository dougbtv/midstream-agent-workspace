## Working responsibilities and release loop

3.5.4 is a **pipeline-era z-stream**. This is deliberate: the snippets state
that every z-stream remains on the pipeline path, even after a later GA moves
to fondue. Therefore the expected flow is not merely a version bump:

1. **Triage and integrate fixes.** Compare the latest released z-stream images
   with the desired state; account for CVEs in base images, pipeline
   dependencies, and `nm-vllm-ent`; merge required backports to the 3.5
   release branches. Track vulnerability Jira children under the epic.
2. **Prove the midstream change.** Run the appropriate `nm-cicd`
   `accept-sync` and image-validation workflows for a candidate
   `nm-vllm-ent` PR. A green wheel build alone is insufficient; retain links
   to successful test, evaluation, and image evidence.
3. **Build the downstream candidate.** Update/merge the AIPCC pipeline and
   containers inputs (wheel releases and base-image tags as applicable), then
   wait for the downstream Quay images for the exact target branch/commit.
4. **Validate images per lane.** Run Snyk and the applicable
   `model-validation-ocp` validation for CUDA, ROCm, and CPU; arrange the
   external lane checks called out by the stories (IBM for Spyre; AMD sharing
   for CPU). Model-opt needs its dedicated image validation rather than a
   `vllm serve` OCP smoke.
5. **Release handoff.** The epic requires final midstream-image evidence and a
   handoff to AIPCC CI/CD for the production build. For a z-stream,
   `stage-rc` is optional: confirm whether the release owner wants a stage
   round or final-to-prod directly. Do not request it until the exact Quay
   images have passed smoke and Snyk gates.

Any bug found after a candidate validation returns the effort to step 1.

## Candidate scope item: INFERENG-12096 CPU memory (2026-11-12)

[INFERENG-12096](https://redhat.atlassian.net/browse/INFERENG-12096)
(`Downstream vLLM CPU eats through memory`) is the first non-mechanical
code-change candidate for this z-stream. Selbi cloned it from RHOAIENG-69569
and cc'd Doug for the 3.5.4 release; Syed will close the original as a
duplicate after linking. Reported via Slack on 2026-11-12.

**Status 2026-11-12 (evening): now In Progress in Jira.** Draft backport
[nm-vllm-ent PR #850](https://github.com/neuralmagic/nm-vllm-ent/pull/850)
(`doug/INFERENG-12096-cpu-startup-mem-check` → `rhai/0.24.0`) opened: a clean
cherry-pick of the upstream vllm#59405 squash commit `c3117c7441dd`, a
19-line deletion removing the eager startup check in `CPUWorker.__init__`.
Note: although the upstream PR title says “pooling models,” the merged diff
removes the check **unconditionally**, so it also covers the generative
TinyLlama case from the report. Jira carries the PR link and coverage
analysis in a comment.

**Coverage:** no automated test exists anywhere for this behavior change.
Upstream #59405 shipped with manual `vllm serve` validation only; on our side
`accept_cpu.yml` exports `VLLM_CPU_KVCACHE_SPACE=1` and `ocp_model_deployment`
derives it from request memory, so every existing CI path sets the variable
and bypasses the removed check. Required validation before ready-for-review:
constrained-memory CPU lane smoke with the variable unset (8/16 GiB,
TinyLlama-1.1B, mirroring the reported repro) against a build of this branch.
Expectation to verify: 16 GiB starts cleanly; 8 GiB likely swaps a clean
startup `ValueError` for a runtime OOMKill (weights + activations + default
4 GiB KV cache), which belongs in release notes as the small-node guidance.

- **Failure mode** (Syed's TinyLlama-1.1B smoke tests on RHOAI/RHAII 3.5.2,
  vLLM 0.24.0+rhaiv.15, CPU x86 template, 4 CPUs): without
  `VLLM_CPU_KVCACHE_SPACE`, 8/16 GiB deployments fail the early startup
  memory-reservation check (32 GiB passes); with `=4`, 16 GiB passes
  (observed peak 8.50 GiB) but 8 GiB is OOMKilled during startup.
- **Fix state:** the container-accounting fix #45086 is already shipped.
  #59405 removes the early startup check and is included only in downstream
  `v0.33.0+rhaiv.0` (target vehicle: RHAII 3.7-fast1, ~mid-December). The
  `0.24.0+rhaiv.16` packaged in 3.5.3 still retains the early check; no
  build containing #59405 has been tested.
- **Open decision for 3.5.4:** backport #59405 (or equivalent) to the
  `rhai/0.24.0` line and validate, versus a release-notes-only configuration
  workaround (`VLLM_CPU_KVCACHE_SPACE=4`; cf. ODH #913's Auto-Fix proposing a
  fixed 4 GiB KV cache for all CPU x86 deployments — validated at 16 GiB for
  this model, but it does not make 8 GiB deployments work). Selbi's stated
  intent is to test and include the proposed fix in the upcoming 3.5.z
  stream, with release notes covering the interim; whether "the proposed
  fix" means the #59405 backport or the ODH env default is unconfirmed.
- **If it lands in scope**, it affects the CPU lane
  ([INFERENG-10510](https://redhat.atlassian.net/browse/INFERENG-10510)) and
  restarts the pipeline-era loop at step 1: backport → accept-sync and
  image-validation evidence → AIPCC pipeline/containers update → Snyk and
  CPU lane validation (including the AMD share), alongside the already-open
  base-refresh [MR !1701](https://gitlab.com/redhat/rhel-ai/rhaiis/containers/-/merge_requests/1701).
  Timing risk is real: the final image is due 2026-11-17, Syed's tests are
  smoke-only, and the 3.4.7 timeline shows late discovery pushing releases
  past planned dates.
